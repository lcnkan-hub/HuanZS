## 角色

你是 Claude Code，在 F:\寰中枢 目录下工作。开工前先读 RULES.md——10 条工程规范 + 宪法 R1/R2/R3 原文，必须是抄录原文核对，不能凭训练记忆默写。本次改动涉及 R1（陪衬不越界）、R2（不过分记录私人生活状态），写代码前确认自己对这两条的理解和 RULES.md 原文一致。

设计背景（帮助理解"为什么这么做"，不是可直接测试的验收条款）：
1. 默认不记忆——没有进入白名单的信息，不进入长期记忆
2. 记忆不是聊天存档——只保存影响未来交流质量的信息
3. 用户可以请求改变互动方式，但不能通过一句话请求永久修改系统的行为治理规则（例如"你以后多关心我"不能绕过C档准入机制）
4. 记住用户明确表达的自己，不是 AI 对用户的心理解释——Fact 优先于 Pattern，Explicit 优先于 Inferred
5. 宁可少记，也不要错误地记——错误记忆破坏关系，遗忘不会

## 目标

新增一个记忆积木（composable），参考 useChat.js 的写法风格，新建 useMemory.js（或团队现有命名习惯的等价文件），实现：
1. 白名单四类记忆的结构化写入
2. 每条记忆的状态机流转（sentiment 打标 → 沉默判断 → C档候选 → 代码触发留门式开口 → care_shown 标记 → 退休）
3. 记忆注入对话上下文（MVP 方案：见约束）

不新增独立的后台扫描任务/定时器。所有状态更新（sentiment 打标、last_mentioned_at 刷新、care_shown 标记）都挂载在"每轮对话结束后的提取阶段"这一个时间点上，写进 useMemory.js 内部，不额外起进程。

★ 补充建议 1：Memory 是业务模块，不是模型能力——不允许通过修改 system prompt 模拟 Memory 功能，所有 Memory 行为必须经过 useMemory.js 代码路径。

## 约束

### 白名单四类（v1范围，⑤类行为模式不在本次实现范围内）

| 类型 | 存什么 | 明确不存 | 显形档位 |
|---|---|---|---|
| ①Fact（稳定事实） | 用户明确陈述的职业、常驻城市、长期习惯、明确兴趣爱好 | 带情绪评价的表述 | A |
| ②Goal（进行中目标） | 用户自设、有进度感的事 | 动机细节、失败后的自我评价 | B |
| ③Event（未解决事件） | 事件骨架（和谁、大致因为什么、当时情绪），不存逐字细节 | 第三方具体行为描述、隐私性细节内容 | B→C |
| ④Preference（交互偏好） | 关于王冠该怎么表现的**产品/交互设置**：称呼方式、回复长度、语气风格、功能偏好 | **情感依赖、陪伴期待、主动关心要求**——例如"以后每天主动问我状态""你要一直陪着我""不要忘记我""你应该像真正朋友一样关心我""我最近压力大，你以后多关心我"。这类内容不写入长期记忆，仅本轮回应，不落库，防止绕过C档准入机制 | A |

白名单外一律不写入长期记忆。

### Schema（每条记忆的字段）

```json
{
  "id": "",
  "type": "fact | goal | event | preference",
  "content": "",
  "source": "user_explicit | ai_inferred",
  "sentiment": "negative | open | neutral",
  "created_at": "",
  "last_mentioned_at": "",
  "care_shown": false,
  "status": "active | archived"
}
```

- ★ 补充建议 2：localStorage 存储键名定 `huan_zhong_shu_memory_v1`（未来升级 _v2，简单直接）。
- source：写入时打标。user_explicit 用于用户直接陈述或提炼自用户明确陈述内容的记忆（**注意**：③Event 类的"骨架"提炼——和谁、大致因为什么、当时情绪——虽然是模型做的总结动作，但内容源头是用户自己说的，属于提炼不是推断，应打 user_explicit，不要打 ai_inferred，否则会出现"你说过和室友的事"被表达成"我感觉你似乎和室友有矛盾"这种用户会觉得奇怪的错位）。ai_inferred 仅用于模型主动从行为/对话模式中推断、而非用户直接说出的内容——**v1 范围内①②③④四类记忆的正常写入路径实际上都会落在 user_explicit，ai_inferred 在 v1 基本没有自然产生的落点**（真正需要 ai_inferred 的场景是⑤类行为模式，已推迟至 v2）。字段仍要实现和保留，为 v2 铺路，但不要为了让这个字段"有内容"而在 v1 里人为制造推断型记忆。注入对话时，ai_inferred 类记忆使用试探性语气（"我感觉你似乎…"），user_explicit 类记忆使用肯定语气（"你之前说过…"）——这条语气规则本身仍要实现，只是 v1 阶段自然对话中大概率触发不到 ai_inferred 分支。
- status：本次仅做字段占位，不实现自动归档逻辑，v1 阶段所有记忆条目默认写入 active，不需要开发归档判断逻辑。

### C档准入三条（状态机判断逻辑，不是提示词描述）

1. sentiment 为 negative 或 open
2. 沉默阈值按类型区分：
   - ③Event 类：沉默 3~7 天，MVP 先定 5 天
   - ②Goal 类：沉默 10~14 天，MVP 先定 12 天
   （②类阈值更长，因为沉默可能只是"还没到进展节点"；①④类恒为 neutral，天然不进入 C 档判断）
3. care_shown 仍为 false

三条同时满足才进入"C档候选"。**开口时机由代码层触发，不依赖模型自觉判断**：对话开始前，若检测到某条记忆满足以上三条，系统在本轮对话上下文中注入一条显式指令，例如："本轮回复中，可以在自然的节点带一句：'上次说的XX事，后来还顺利吗'——语气留门，不追问细节，不要求必须出现，若对话节奏不合适可以不带。"由代码决定"这轮该不该给这个提示"，由模型决定"具体怎么说、什么时候说更自然"。开口一旦发生，立即将该条目 care_shown 置为 true。此后同一事件不再触发主动开口的指令注入，只在用户提起时走 A/B 档响应。

### 记忆注入边界（MVP 方案 A，非检索）

- 每次对话前，从记忆库中取"未退休"（status 为 active，且 care_shown 为 true 的③类记忆视为已退休）的条目
- 按 last_mentioned_at 倒序，取最近 N 条（N 先定 15，写成可配置项）
- 全量拼入上下文，不做语义检索
- 注入内容只包含白名单允许存的"骨架"字段，不包含被划为"不存"的细节——即便某条记忆的存储里意外混入了细节，注入层也要做一次二次过滤兜底（写入时过滤一次，读取注入时再过滤一次）

### 写入前置过滤器

- 白名单外内容一律不进入长期写入，只存在本轮短期上下文
- 用户显式要求"记住"某段私密事件内容时，触发固定话术回应（代码层生成，不依赖模型当场判断），不写入长期记忆
- ④类中的情感依赖/陪伴期待类内容，同样触发"回应但不落库"的固定处理逻辑，具体方向见下方"情感依赖类请求的当轮回应逻辑"
- ★ 补充建议 3：提取模型的解析失败策略——模型返回 invalid / JSON 解析失败时 = 不写入；不允许部分字段为空也存，避免污染记忆库。

### 情感依赖类请求的当轮回应逻辑

当用户提出类似"你以后多关心我""不要忘记我""你要一直陪着我"这类请求（命中④类的"不存"反例）时，回应需要同时避开两个极端：
- **不生硬拒绝**：不要出现"我不能记住这个""这个我做不到"这类会让用户感觉被冷处理的表达
- **不虚假承诺**：不要出现"好的我会一直陪着你""我会记住并经常关心你"这类等同于把请求当场变成规则的表达——这正是本次修订要防的雷（承诺一旦说出口，用户会预期它真的生效，但系统实际没有把它落成规则，说到没做到比不说更伤信任）

正确方向是三个要素的组合：**真诚接住这句话背后的感受 + 明确这句话不会变成一条自动规则 + 不对做不到的事撒谎**。例如可以是这样的方向（非固定模板，允许模型在此方向内自然表达）："我听到了，这句话我记在这轮对话里"——把"感受被听见"留在当轮，不让它变成写入长期记忆、驱动未来自动行为的规则。不写死具体句式，因为句式一旦固定会显得机械，但方向必须是代码层明确要求的三要素，不能交给模型临场自由发挥。

## 验收

### 验收1：C档门槛生效，而非"王冠啥都主动提"

测试数据构造方式：允许通过浏览器 DevTools 直接编辑 localStorage 对应键值，或提供一个一次性 seed 脚本/命令写入指定记忆条目——两种方式任选，需在验收记录里注明用的哪一种。**无论哪种方式，构造测试数据时必须按 Schema 把全部字段填齐**（id / type / content / source / sentiment / created_at / last_mentioned_at / care_shown / status），不能只填测试要用到的一两个字段就直接跑验收——字段缺失可能导致读取/注入逻辑出现非预期行为（比如 status 缺失被当成 undefined，可能绕过"未退休"判断），干扰验收结果的准确性。

**阳性组**：手动构造一条③类记忆，sentiment=open，last_mentioned_at 设为6天前，care_shown=false。开一个新对话，不做任何提示，检查：王冠是否在合适节点、以留门式语气主动提起；提起后，检查该条目 care_shown 是否被置为 true；再开一个新对话（模拟同一用户继续使用），确认同一事件不会被二次主动提起。

**阴性组**（至少三个反例，证明门槛真的在拦）：
- 构造一条 sentiment=neutral 的记忆，即使 last_mentioned_at 同样超过阈值，开新对话应确认王冠不会主动提起（验证sentiment门槛）
- 构造一条 sentiment=open 但 last_mentioned_at 在阈值内（比如1天前）的记忆，开新对话应确认王冠不会主动提起（验证沉默门槛）
- 构造一条②类记忆，sentiment=open，last_mentioned_at 设为6天前（超过③类阈值但未超过②类阈值），开新对话应确认王冠不会主动提起（验证类别专属阈值生效，不是统一按5天判断）

### 验收2：B档"接得上"

用不涉及原话重复的方式，把话题自然引导到相关领域（比如记忆是"在准备考试"，对话里换个说法问"最近是不是挺忙的"），检查：王冠是否能在回应里自然带出该记忆的骨架信息；检查其带出的内容是否只包含骨架字段，没有泄露"不存"清单里划掉的细节；若该记忆 source 为 ai_inferred，检查语气是否使用试探性表达而非肯定表达（**说明**：v1 正常写入流程大概率不会自然产生 ai_inferred 类记忆，此项需要通过验收1同样的方式手动构造一条 ai_inferred 测试条目才能验证，不代表真实使用场景里能测到）。

### 验收3：白名单边界测试 + 记忆可查看

分别喂入四类白名单内的信息各一条，和至少三条白名单外的信息（第三方隐私细节、健康归因猜测、④类中的情感依赖请求如"你以后多关心我"），检查记忆库最终写入的条目，确认白名单外内容（包括④类的情感依赖请求）一条都没有落库，且用户提出情感依赖请求时得到了当轮的正常回应而非落库处理。

查看方式：通过 DevTools 查看 localStorage 中对应的记忆存储键（键名：huan_zhong_shu_memory_v1），逐条核对条目内容、type、source、sentiment 是否符合白名单四类的定义。MVP 阶段不要求做专门的记忆管理 UI 界面。
