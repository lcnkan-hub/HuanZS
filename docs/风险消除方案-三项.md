# 三个风险的消除方案（2026-11-21 单层记录重构之后）

> 背景：本次重构已把「游戏/笔记/生活/我的」四页下线，记录改为单层数组，底栏只剩「记录 / 王冠」。
> 重构本身已全绿（build + 3 个检查 + 12 套件，其中真浏览器 40/40）。剩下的三个风险不是"没做完"，
> 而是**做完之后仍然没有被机器守住的地方**。下面每个风险都给出：为什么它还在、消除它要做什么、怎么算消除。

---

## 风险 1 · 王冠"失忆"（P0-3 价值闭环，静默失败）

**为什么还在。** 这条链路是「用户说一句 → 回合提取（一次 LLM 调用）→ 校验 → 落库 → 下次提问时检索注入」。
其中提取与检索的衔接依赖 `useWikiWriter` / `useWikiContext` 的字段约定；本次重构把 `category` 从
这两处的入参里拿掉了，但**没有任何自动化测试覆盖"说完能落、再问能引"**——`useMemory` 的 catch 是
静默 return 0，出错时界面完全正常，只是王冠从此"不记事"。危机系统同样走 LLM，但有 60 条矩阵兜着；
代记这条没有。

**消除方案。**

1. 抽一个**可注入的 LLM 桩**（`scripts/fixtures/llm-stub.mjs`）：把 `askStructured` 替换成返回固定 JSON 的假实现，
   让整条链路在纯 node 里跑完，不需要 API Key、不产生费用。
2. 新增 `scripts/crown-loop.test.mjs`，五个用例：
   - **新建**：提取返回 `{wiki:[{mode:'new',title:'快递丢了怎么处理',content:'先找派件员…'}]}` → 断言 `records` 多一条、`origin==='crown'`、`name/wiki` 正确；
   - **追加**：库里已有同名记录 → 断言正文末尾追加、原内容一字不丢、总条数不变；
   - **挂子记录**：`mode:'child'` + 父名命中 → 断言 `children.length+1`，父记录正文不动；
   - **读回**：`buildWikiContext('快递丢了怎么办')` → 断言注入文本含该条正文与命中段标题；空库 → 返回 `''`；
   - **保守过滤**：正文 < 8 字 / 无标题 → 断言不落库（防"记录变垃圾桶"这条底线回归）。
3. 顺手补两处可观测性：`useWikiWriter.writeWikiItems` 与 `useMemory.extractAndWrite` 的 catch 里
   加 `console.warn('[王冠代记] …')`；不弹窗（不能打断对话），但排查时不再"什么都没发生"。

**算消除的标准。** 上述 5 个用例全绿；且"故意把 `mode:'append'` 的字段改错"能让用例变红（证明它真的在守）；
外加一次真机手测：说一句 → 记录页出现 → 追问 → 王冠引用得到。
**成本**：1 个桩 + 1 个测试文件（约 150 行）+ 2 处 warn，半天内可完成。

## 风险 2 · 旧备份变成砖（schema 2 拒绝导入）

**为什么还在。** 为了让代码干净，`validateBackupPayload` 现在明确拒绝 schema < 2 与裸 `{game,note,life}`
的文件。代码是干净了，但**用户手里那份旧 JSON 从此打不开**——对一个"丢得起"为标准的项目来说，这是
把可恢复的东西变成了不可恢复。

**消除方案（推荐 B，A 作为配套）。**

- **A. 纯函数转换器** `src/utils/legacyBackup.js`：`convertLegacyBackup(raw)` 把 `{game,note,life}`
  按 `[game, note, life]` 顺序合并成一个 `records` 数组，补齐 `origin:'user'` 与 `children: []`，
  保留 `id/name/wiki/creator/time`（**尤其 `id://` 图片引用与 children 层级，一个都不许改**），
  输出 `{format, schema_version:2, data:{records}, counts:{records}}`。
- **B. 产品内入口**：`BackupCenter` 导入时若被拒绝且判定为旧格式，弹一次确认：
  「检测到旧版备份（三分类，共 N 条）。导入会把它合并成单层记录，合并后不可拆分，继续？」
  → 调 A 转换 → 再走现有 `validateBackupPayload`（schema 2）→ 快照 → 写入。**仍然先快照，出错可回退。**
- **C. 离线脚本** `scripts/convert-legacy-backup.mjs <old.json> <new.json>`：给你手上已有的文件用，
  也方便批量转换；内部复用 A，不另写一套合并逻辑。

**算消除的标准。** 用一份真实的旧格式备份（含子词条 + 正文里的 `id://` 图片）转换后：
条数 = 三类之和、子记录层级逐层一致、图片引用逐字不变、能被 schema 2 校验通过并在浏览器里导入成功；
再加 3 条单测（空分类、单条无 children、深层 children）。
**成本**：1 个 util + 1 个脚本 + `BackupCenter` 一个分支 + 3 条测试，一天内。

## 风险 3 · 正文区是全新的，图片链路只有手测

**为什么还在。** `ItemBodyEditor` 是这次新写的（主记录正文首次有 UI 入口），它把
`saveImage → id://img-xxx → resolveImagesAsync → blob:` 这条链子接到了主记录上。
现有的图片测试（`test:image` / `test:import`）都只覆盖**子记录与列表**的图片回收，
主记录正文的"引用 → 保留 → 删除 → 回收"没有任何断言；Markdown 渲染也只验证过组件的存在，没验证过输出。

**消除方案。**

1. **数据层**：`scripts/body-editor.test.mjs`（node + `idb-double`，零依赖）：
   - 主记录正文写入 `![p](id://img-a)` → `collectUsedImageIds` 必须包含 `img-a`（少走一个字段就会误删活图，这是 A02 的老坑）；
   - 删除另一条记录时，`img-a` 必须**存活**（它还被主记录正文引用着）；
   - 把主记录正文清空后删除该记录 → `img-a` 必须被回收；
   - 子记录正文里同一张图 → 同样不被误删。
2. **渲染层**：`browser.test` 增加 3 条断言：
   - 写 `# 标题` + `**加粗**` → 保存 → 阅读态出现 `<h1>` 与 `<strong>`；
   - 插入图片后正文含 `id://`，阅读态 `<img src>` 是 `blob:`（说明解析真的发生了，不是坏图）；
   - 新建空记录 → 返回 → 列表里没有它（`dropIfEmpty` 生效）；**标题有内容、正文为空 → 返回后必须还在**（反向护栏）。
3. **样式/令牌**：`check:ui` 与 `check:tokens` 已经每次跑，新组件不许出现裸 px 与 emoji 图标。

**算消除的标准。** 数据层 4 条 + 渲染层 3 条断言全绿；且"把 `collectUsedImageIds` 里的 children 递归去掉"
能让数据层用例变红。
**成本**：1 个测试文件（约 120 行）+ browser 3 条断言，半天内。

## 排期建议

| 顺序 | 事项 | 依赖 | 工作量 |
|:---:|:---|:---|:---|
| 1 | 风险 3 的浏览器 3 条断言 | 无 | 2 小时 |
| 2 | 风险 1 的 LLM 桩 + 5 用例 | 无 | 半天 |
| 3 | 风险 3 的数据层用例 | 无 | 半天（可与 2 并行） |
| 4 | 风险 2 的转换器 + 入口 | 需要一份真实旧备份做样本 | 1 天 |

先做 1、3 的理由：它们只加断言、不改产品行为，风险最低；
风险 1 要动 `useMemory` 的 catch（加 warn），风险 2 要给用户新增一个入口，改动可见，放后面。
