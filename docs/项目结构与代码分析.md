## 7. 发现与建议

### 7.1 站得住的部分

- **分层方向是对的。** fan-in 最高的三个文件 `constants/categories.js`（20）、`common/AppIcon.vue`（17）、`utils/storageScope.js`（9）都是"底座"型积木，没有出现"某个业务组件被到处引用"的倒挂。
- **冻结区纪律真实存在。** `crisis.js` / `crisisContextPatterns.js` / `riskStateMachine.js` 三个文件头都写着【冻结物 · 改动须重跑测试矩阵】，与 RULES 第 11 条对得上。
- **测试密度不低。** 13 个测试套件 + 3 个检查脚本 + 7 个运行器，覆盖了危机矩阵、备份回滚、主动开口、存储健康、跨标签页同步这些最容易出错的地方；`TODO` / `FIXME` 为 0。
- **依赖极薄。** 运行时只有 `vue`（24 个文件）与 3 个 Capacitor 插件（仅 `useBackup` 动态导入），与 README「零依赖」的说法一致。

### 7.2 需要注意的四件事

**（1）有一条循环依赖，方向是"服务层反向依赖逻辑层"**

```
composables/useChatAI.js → services/crisisResponse.js → services/crisisDetection.js → composables/useChatAI.js
```

`crisisDetection.js` 的文件头注释写明：L2 语义确认「复用 askStructured」，紧接着第 9 行就是 `import { askStructured } from '../composables/useChatAI'`。所以这是**有意为之的复用**，不是手滑——但方向仍然反了：检测层为了做模型二次判定，反过来依赖了 AI 请求积木。后果不是立刻会崩，而是：**危机管线再也无法脱离 UI/逻辑层单独测试与替换**，而且改动 `useChatAI` 的导出会连带影响 RULES 第 11 条保护的冻结区。

建议：把 `askStructured` 下沉成 `services/llmClient.js`（只做"发一次结构化请求"），`useChatAI` 与 `crisisDetection` 都依赖它。注意这属于触及危机结构，**同一提交必须带 `npm run test:crisis` 全量矩阵**。

**（2）三个超大文件，已经在违反自己定的规则**

| 文件 | 行数 | 问题 |
|:---|---:|:---|
| `composables/useBackup.js` | 794 | 导出、导入、校验、图片救援、Capacitor 分支挤在一起，导出 18 个符号 |
| `components/crown/ChatView.vue` | 708 | 消息流、输入框、记忆面板开关、开场引导、AI 设置入口全在一个 SFC |
| `App.vue` | 515 | 页面编排 + 通知条 + 备份提醒 + 主动开口触发 + 账号门都在这里 |

RULES 第 3 条说"不允许大规模重构"、第 8 条说"不往现有大文件里塞代码"——这两条正在互相抵消：**不重构**使得新功能只能往大文件里塞。建议按"可单测性"排序拆，先拆 `useBackup`（纯逻辑、`backup.test.mjs` 已有 299 行断言兜底），再拆 `App.vue`（抽 `useAppShell`），最后动 `ChatView`（需真浏览器验收）。

**（3）存储访问没有真正收口**

`src/services/storageAdapter.js` 只被 4 个文件引用，但 `localStorage` 在 20 个文件里出现了 **72 次**，其中直接访问最重的是：

| 文件 | `localStorage` 出现次数 |
|:---|---:|
| `useBackup.js` | 13 |
| `useAccount.js` | 12 |
| `useWikiData.js` | 10 |
| `useLocalStorage.js` | 9 |
| `storageAdapter.js` | 7 |
| `useChat.js` | 7 |

这意味着"账号隔离（`storageScope` 加后缀）"与"未来换存储（WebDAV / 后端 / SQLite）"这两件事都没有唯一入口。P0-2 真做同步时，最先要付的账就是这 72 处。

**（4）文档落后于代码**

- `PROJECT.md` 积木清单漏了 7 个文件：`NoticeBar.vue`、`CrownBackdrop.vue`、`backupReminder.js`、`retrievalSelect.js`、`storageHealth.js`、`storageSync.js`、`textMatch.js`（后 5 个都是 10 月中旬之后新增的"第二批"积木）。

- `RULES.md` 第 3 条写"27 文件的积木架构已定型"，实际 68 个源文件。

## 附：统计方法与口径

- **行数**：文件物理行数（含空行与注释），`.vue` 计整个 SFC，不区分模板/脚本/样式。
- **依赖 / fan-in**：解析 `import ... from '...'` 与动态 `import('...')`，只解析相对路径，扩展名自动补 `.js` / `.vue` / `/index.js`；`fan-in` = 被多少个 `src/` 内文件直接 import。
- **循环依赖**：对导入图做 DFS，记录回边（back edge），非强连通分量算法，可能合并多条同环路径。
- **文档对账**：以文件基名（去扩展名）在 `PROJECT.md` 文本中出现与否判定"是否被清单覆盖"，所以"清单里提了名字但没写 `.vue`"算覆盖。
- **未纳入**：`android/`（Capacitor 生成物，69 个文件）、`docs/`、`public/`、`.hermes/skills/`、`scripts/` 只在目录树中列出，不做逐行分析。
- 本文件可随时重跑：分析脚本留在会话临时目录，如需固化可移入 `scripts/` 变成 `npm run report:struct`。
